# File formats

Crystal Builder reads and writes seven structure formats, and each
one keeps a different part of what a structure is.  After this page
you know which format to reach for, what a round trip through it
loses, why a CIF written here carries its bonds, and what a project
file holds that no CIF can.

## The list

```{index} single: file formats; list
```

`xtal formats` prints the formats the application knows, and whether
each is read, written or both:

```console
$ xtal formats
name   read  write  extensions
cif    yes   yes    .cif .mcif
xtalproj yes   yes    .xtalproj
poscar yes   yes    .poscar .vasp
pmg-json yes   yes    .json
cssr   yes   yes    .cssr
gen    yes   yes    .gen
xyz    yes   yes    .xyz .extxyz
```

The same registry builds the filter of {ref}`Open… <cmd-open>` and
the format picker of {ref}`Export… <cmd-export>`.  A VASP file is
also recognised by its whole name, `POSCAR` or `CONTCAR`, which has
no suffix to match on; the name is tried first and exactly, so a
`POSCAR.cif` is a CIF whatever its stem says.  Three more formats are
read or written by one feature each and are deliberately not in the
list, because none of them is a structure: the `.cgd` net Systre
reads ({doc}`/frameworks/nets`), the PDB that Blender is handed
({doc}`stl`), and the `.xy` diffraction pattern and Gaussian `.cube`
field the porosity and PXRD pages overlay
({doc}`/porosity/index`).

## What each format keeps

```{index} single: file formats; what is lost
```

The *Export* dialog says, under its picker, what the chosen format
keeps and what it drops.  The sentences are computed from the
registry, so they are the application's own answer rather than a
table that could drift from it:

- *CIF keeps symmetry, occupancy, displacement parameters and
  charges; bonds and the view are not written.*
- *POSCAR keeps the atoms and the cell; symmetry, occupancy,
  displacement parameters, charges, bonds and the view are not
  written.*
- *PMG-JSON keeps occupancy; symmetry, displacement parameters,
  charges, bonds and the view are not written.*
- *CSSR keeps charges; symmetry, occupancy, displacement parameters,
  bonds and the view are not written.*
- *GEN keeps the atoms and the cell; symmetry, displacement
  parameters, charges, bonds and the view are not written.*
- *XYZ keeps occupancy; symmetry, displacement parameters, charges,
  bonds and the view are not written.*

A project, which is not offered by *Export…* because it is what
*Save* writes, keeps all six.  "Bonds are not written" is said of the
CIF because a CIF that leaves through *Export…* is cleaned first --
the next page, {doc}`export`, is about that door -- while the CIF in
the {term}`workspace` does carry them, as the next section explains.

## CIF

```{index} single: CIF; reading
```
```{index} single: CIF; writing
```

The Crystallographic Information File {cite}`hall1991cif` is the
interchange format of crystallography and the one this application
is built around: a CIF holds an {term}`asymmetric unit` and a
{term}`space group`, which is exactly the data model, so the read is
close to a straight copy.  Reading and parsing go through gemmi
{cite}`wojdyr2022gemmi`; writing is done by hand, so that the file is
line for line what the application intends.

### What a written CIF contains

A CIF written here is deliberately minimal -- cell, symmetry, atoms,
bonds, and a note saying which program produced it.  No refinement
history, no diffractometer block, no invented uncertainties: writing
tags the application did not compute would dress a built model up as
a measurement.  The header of `MIL-53.cif` from the COD
{cite}`grazulis2012cod`, written back out by `xtal convert`:

```
# Generated by Crystal Builder 0.3.1.dev49+g0db248ed6.d20260926
# Structural data only: cell, symmetry and atomic sites.

data_1502688

_audit_creation_method    'Crystal Builder 0.3.1.dev49+g0db248ed6.d20260926'
_audit_creation_date      2026-09-26
_chemical_formula_sum     'C32 Cr4 D16 O20'

_cell_length_a            16.772000
_cell_length_b            13.145000
_cell_length_c            6.847000
_cell_angle_alpha         90.0000
_cell_angle_beta          90.0000
_cell_angle_gamma         90.0000
_cell_volume              1509.5440

_space_group_name_H-M_alt 'I m c m'
_space_group_name_Hall    '-I 2 2a'
_space_group_IT_number    74

loop_
_space_group_symop_id
_space_group_symop_operation_xyz
   1  x,y,z
   2  -x,-y,z
[...]
```

The atom-site loop follows, with the label, the type symbol (the
element with its oxidation state where a site has one, `Ti4+`, which
is how a CIF keeps charges), fractional coordinates, the
{term}`occupancy`, and `_atom_site_U_iso_or_equiv` when any site has
an isotropic displacement parameter; an `_atom_site_aniso_*` loop is
written when any site has anisotropic ones.  With *P1 (every atom
written out)* the same file lists every atom of the cell under the
identity operation alone.

### Which symmetry the reader believes

```{index} single: CIF; space group statement
```

Files in the wild carry several symmetry statements, and they do not
always agree.  The reader takes them in a fixed order: a Hall symbol
(unambiguous, and always wins); the symmetry-operation loop
(unambiguous about the *setting*); an H-M symbol or an International
Tables number (ambiguous about origin and axes); and nothing at all,
which is {term}`P1` with a warning.  The operation loop is preferred
when it identifies a group of the same order as the symbol names, and
the symbol wins otherwise; every disagreement is recorded and shown
in the window when the file opens, so a file that says two things is
never read in silence.  A Hall symbol written with semicolons or
commas for its spaces (`-F 4;2;3`) is repaired and the repair is
reported; a quoted integer in `_space_group_IT_number`, which every
CIF the RCSR's generator writes carries, is read rather than refused.

### The CIF carries the bonds

```{index} single: CIF; bonds (_geom_bond)
```
```{index} single: _geom_bond
```
```{index} single: _xtal_bond_kind
```

:::{note}
**The CIF carries the bonds.**  `_geom_bond` says (site, site,
operation, translation) and always could, so the CIF in the workspace
*is* the document: the {term}`dummy atoms <dummy atom>` you placed
and the {term}`net` you drew over a framework are in the file.  What
a bond *means* to this application rides in `_xtal_bond_*` tags in
the same loop, which every other CIF reader skips.
:::

The standard half of the loop is the whole geometry.
`_geom_bond_site_symmetry_2` is the `n_pqr` code -- operation *n* of
the symmetry loop above, then a lattice translation of
(*p*−5, *q*−5, *r*−5) -- which is a bond's operation and image with
nothing left over, so another program reads the bonds this one drew.
Three things standard CIF has no vocabulary for follow it: the order,
whether the order was *stated* by you or inferred, and the kind -- a
{term}`topology bond` is not a chemical bond, and a
{term}`suppressed bond` is the record of one deliberately deleted.
The image is repeated in `_xtal_bond_image` because `n_pqr` has one
digit per axis and cannot spell a translation of five cells or more,
which a net edge is under no obligation to stay inside; a bond that
does not fit gets `.` in the standard column and is still complete.
One hand-drawn Cr–O bond on MIL-53, as written:

```
loop_
_geom_bond_atom_site_label_1
_geom_bond_atom_site_label_2
_geom_bond_site_symmetry_2
_geom_bond_distance
_xtal_bond_image
_xtal_bond_order
_xtal_bond_kind
_xtal_bond_stated
O1       CR1      1_555      1.8336  0,0,0       1.000 explicit     no
```

The private tags are also the *signal*:

:::{note}
**A foreign `_geom_bond` loop is not read as bonding.**  Plenty of
published CIFs carry one, and it is nearly always a *distance table*
from the refinement -- a selection of contacts somebody chose to
tabulate, not the bonding of the crystal.  Reading it in as the bond
graph would hand you a structure bonded by whoever prepared the file,
silently, on open, which is the one thing {ref}`Recalculate bonds
<cmd-recompute_bonds>` exists to stay in charge of.  The reader takes
a bond loop only when `_xtal_bond_kind` is in it; a loop without that
tag is left alone and the structure opens with no bonds until you ask
for them.
:::

Every row is taken by label, and a row that does not read -- an atom
the site loop no longer has, a site bonded to itself in its own
image, an operation the group does not have -- is dropped on its own.
A bond loop that has drifted out of step with the atoms is a file to
open without its bonds, not a file to refuse.

### The perceived graph a scan point carries

```{index} single: CIF; perceived bonds (_xtal_perceived_bond)
```

Bonds are recalculated only when you ask, so what a CIF normally
records is the bonds you drew; the {term}`perceived graph <perceived
bonds>` is worked out again when the file opens.  A point of a
{term}`relaxed scan`
({doc}`/structure/scans`) is the one file for which that is wrong: its
cell is not the one the bonds were perceived at, and opening it would
perceive again at the stretched geometry.  Measured on the shipped
`MIL53.cif` sample at +15 % on *a*, that opens with 24 of its 126
bonds gone.  So a scan point's CIF also carries the graph, as an
`_xtal_perceived_bond_*` loop of P1 bonds under an
`_xtal_perceived_cell_atoms` count, written against the coordinates
as printed.

The reader accepts that loop only if it still describes the atoms in
front of it: the count must match the expanded cell, and every bond
must be within 0.01 Å of the length it was written at.  A file edited
by hand fails that test and is opened the old way, perceived afresh,
rather than bonded to atoms that are not the ones meant.  It is the
answer perception gave, not a new rule: *Recalculate bonds* still
replaces it with a perception at the geometry it sees.  Ordinary
saves and exports never write this loop; a CIF from anywhere else is
unchanged by it.

### More than one crystal in a file

```{index} single: CIF; several data blocks
```

The CSD and most refinement programs ship a series as one CIF with
several `data_` blocks.  Block one is what opens, and the file saying
that it holds more is a warning on it -- *`series.cif` holds 4
structures; the first (block 1) was opened* -- shown in the window
rather than discovered later.  A block that declares no atom-site
loop is metadata (a journal reference, a publication table) and is
skipped; a block with the loop and no rows in it is a crystal with no
atoms yet, which is what {ref}`New <cmd-new>` writes into the
workspace, and it opens.  On the command line, `xtal` reads the first
block too.

### mmCIF

```{index} single: mmCIF
```

The small-molecule and macromolecular halves of a CIF are two
vocabularies -- `_atom_site_fract_x` against `_atom_site.Cartn_x` --
and gemmi speaks both.  When a file yields no small-molecule block,
the reader tries it as mmCIF/PDBx {cite}`westbrook2000mmcif`, and
only then, so an ordinary CIF never reaches that path.  What is kept
is what this application is about: the cell, the space group and the
atoms of the first model.  The chain, residue and entity hierarchy is
dropped; an atom's name within its residue becomes the site label,
suffixed with the residue number, which is what makes a metal site
findable afterwards; the B factor is converted to U.  The extension
is still `.cif` (or `.mcif`).

### Encodings

```{index} single: encoding; byte-order mark
```
```{index} single: encoding; Latin-1
```

Notepad, Excel, PowerShell's `Out-File` and a good deal of Java
crystallography tooling put a byte-order mark at the front of a UTF-8
file, and read naively those three invisible bytes become the first
character of line one -- a perfect CIF was *expected block header*, a
perfect XYZ *must be an atom count*.  Every reader here strips the
mark; a CIF that starts with one is decoded first and handed to gemmi
as text, and one without it is handed over as the file.  A text file
that is not UTF-8 at all -- a pre-2010 CIF or XYZ written in Latin-1
-- is refused with the file named and the byte located, rather than
with a decoder's offset:

```text
café.xyz is not UTF-8 text (byte 61 is 0xe9); re-save it as UTF-8
```

## The project file (.xtalproj)

```{index} single: project file (.xtalproj); contents
```

A CIF holds a structure.  A project holds the {term}`session`: the
structure plus how you were looking at it and what you had done to
it.  {ref}`Save File <cmd-save>` writes one, and a document opened as
a CIF becomes the `.xtalproj` of the same name on its first save
({doc}`/essentials/file`).  The file is a zip of small, readable
parts -- a project should still be openable in five years and
diffable today, and every part can be read with an editor:

```{tabularcolumns} |\Y{0.2}|\Y{0.8}|
```

| Part | What it holds |
|---|---|
| `structure.cif` | the crystal, in the interchange format above, bonds included |
| `cell.json` | the bare cell, written only when there are no atoms yet -- a CIF with no sites is not a CIF |
| `bonds.json` | the perceived graph and the bond rules it was perceived under, and the hand-drawn and suppressed bonds again |
| `sites.json` | the per-site extras a CIF has nowhere to put, such as a hand-set {term}`atom type` |
| `view.json` | the view: style, colours, display range, background |
| `session.json` | the selection, the selected bonds, the measurements, the planes, a pore network or a charge overlay if one was on the structure, and the format header |

`xtal convert` writes one from any structure file, and a fresh one is
four parts:

```console
$ xtal convert resources/samples/cod/MIL-53.cif MIL-53.xtalproj
wrote MIL-53.xtalproj: CrD4C8O5, 7 sites, 72 atoms, Imcm
$ unzip -l MIL-53.xtalproj
  Length      Date    Time    Name
---------  ---------- -----   ----
     1554  09-25-2026 23:22   structure.cif
       35  09-25-2026 23:22   bonds.json
        2  09-25-2026 23:22   view.json
       40  09-25-2026 23:22   session.json
[...]
$ unzip -p MIL-53.xtalproj session.json
{
 "format": "xtalproj",
 "version": 1
}
```

The header is versioned, and the reader is tolerant on purpose.  A
project written by a later version is read as far as it can be rather
than refused: the structure is the part that matters, and losing a
view setting is not a reason to lose a crystal.  A bond in
`bonds.json` that no longer fits the structure is dropped with a
warning naming it (*unreadable bond*), not a reason to fail the open;
a measurement or a plane that points at an atom that is not there is
left out rather than restored wrong.  A zip that has no
`structure.cif` in it is *a zip but not a project*, and is refused by
name.

:::{note}
A project stores the perceived graph as well as the bonds you drew.
Reopening a project used to perceive again from the geometry as it
then was, so a graph you had recalculated -- and were relying on --
could come back different from the one you saved.  Now it comes back
as saved, and {ref}`Recalculate bonds <cmd-recompute_bonds>` is still
the only thing that changes it.
:::

## VASP POSCAR and CONTCAR

```{index} single: POSCAR
```
```{index} single: CONTCAR
```

VASP's {cite}`kresse1996vasp` geometry file is positional: a comment,
a scale, three cell vectors, the species and their counts, then a
word saying whether the coordinates are `Direct` (fractional) or
`Cartesian`.  The reader takes both, steps over a *Selective
dynamics* line, and honours a negative scale as a volume in Å³ rather
than a length, which is what VASP does with it.  Two things are worth
knowing before you hand one over:

- **A file without a species line is refused.**  VASP 4 wrote the
  counts alone and took the names from the POTCAR beside it; there is
  no POTCAR here, and reading the atoms as `X` would be worse than
  refusing, because `X` is a marker and every force field would hold
  the whole crystal back at the door.
- **A POSCAR is P1 by construction.**  Symmetry is not in the file at
  all, so what is written is the expanded cell in `Direct`
  coordinates, grouped by element because the counts line is the only
  species information there is, and what is read back is P1.
  {ref}`Find symmetry… <cmd-find_symmetry>` is how the group is found
  again; the worked example below shows it.

## pymatgen JSON

```{index} single: pymatgen (JSON)
```

pymatgen {cite}`ong2013pymatgen` serialises a `Structure` as a
JSON object carrying `@module` and `@class` beside a lattice matrix
and a list of sites, each with its species, occupancies and
fractional coordinates.  Crystal Builder reads and writes that shape
**without importing pymatgen**: the format is documented and the half
a crystal needs is small, so the door onto pymatgen -- and onto ASE
and anything else that has learned the dict -- costs no dependency.
Partial occupancy survives in both directions.  Symmetry does not: a
pymatgen `Structure` is a list of sites in a cell with nowhere to
record a space group, so the file is P1 both ways.  A JSON file
holding some other pymatgen class is refused by its name (*this is a
pymatgen Molecule, not a Structure*).

## Extended XYZ and trajectories

```{index} single: XYZ (extended)
```
```{index} single: trajectory; extended XYZ
```

Plain XYZ carries no cell, so a crystal through it loses the lattice.
The {term}`extended form <extended XYZ>`, with `Lattice="..."` on the
comment line, is what
ASE {cite}`larsen2017ase`, OVITO and VMD write, and it round-trips.
What is written is the expanded cell in cartesian Å with a
`Properties=species:S:1:pos:R:3:occupancy:R:1` column list, so the
occupancy travels; a file *without* a `Lattice=` entry is read into a
P1 box with 5 Å of vacuum around the atoms and a warning saying so,
which is the only honest thing to do with it.  This is also the
format the clipboard uses, so copy and paste between this application
and any other atomistic tool works.

A relaxation is many XYZ frames in one file, each with its own
comment line, and everything else on that line is `key=value` -- the
energy of a frame travels with it, and an unknown key is carried
rather than lost.  A run's own `trajectory.extxyz`, an ASE `.traj`
(which needs the `ase` extra) or a LAMMPS dump converted to extxyz
opens in the {ref}`Trajectory <panel-trajectory_dock>` panel by
double-clicking it in the *Workspace* tree, and is played against
the structure in front.  A frame is not an editable structure: the
document refuses edits while one is showing, and the bar offers
*Adopt this frame* (one undoable step) or *Close* (the atoms back
where they were).  A trajectory of a *different* crystal is refused;
matching atom counts alone would let one run drive another
structure.

## CSSR

```{index} single: CSSR
```

CSSR exists here because it is what Zeo++ {cite}`willems2012zeopp`
reads ({doc}`/porosity/zeopp`), and it is worth having anyway as the
smallest complete description of a periodic crystal: six numbers for
the cell, then an element and three fractions per atom.  **It is
written in P1, always**, with `1 P 1` in the space-group field,
because every reader of the format ignores that field and treats
what it is given as the whole cell -- an asymmetric unit written into
it would not be a lossy export but a wrong one, and Zeo++ would
compute the porosity of two atoms in a box.  A charge per atom is
written into the field the format has for it.  Occupancy is not
representable, and a partially occupied site would be written as a
whole atom; the Porosity module refuses such a structure before the
writer is reached rather than tell that lie for you.

## DFTB+ geometry (.gen)

```{index} single: gen file (DFTB+)
```

DFTB+ {cite}`hourahine2020dftbplus` reads `.gen`: an atom count and a
kind letter, a species line, then numbered atoms naming their element
by index into that line.  `C` is a cluster with no cell, `S` a
supercell in cartesian coordinates, `F` a supercell in fractional
ones.  All three are read; `F` is written, because fractional
coordinates are what the application stores and a round trip through
cartesian is drift in the last digit.  Like CSSR it holds no space
group, so it is P1 both ways.  It is also how a DFTB+ relaxation
comes back ({doc}`/energy/dftb`): `geo_end.gen` is the final geometry
in the same format as the input.  A structure with no atoms cannot be
written to it, and the error says to add some or export to CIF.

## Worked example: a round trip through two formats

```{index} single: xtal convert; round trip
```

The shipped COD copy of MIL-53 {cite}`mulder2010mil53`, written in
*Imcm* with seven sites, taken through POSCAR and then extended XYZ:

```console
$ xtal info resources/samples/cod/MIL-53.cif
formula        CrD4C8O5  (Z = 4)
space group    Imcm (#74, orthorhombic)
cell           a=16.7720  b=13.1450  c=6.8470
               alpha=90.000  beta=90.000  gamma=90.000
volume         1509.544 A^3
sites / atoms  7 / 72
mass           944.540 amu
density        1.0390 g/cm^3
title          1502688
$ xtal convert resources/samples/cod/MIL-53.cif MIL-53.poscar
wrote MIL-53.poscar: CrD4C8O5, 7 sites, 72 atoms, Imcm
$ xtal convert MIL-53.poscar MIL-53.xyz
wrote MIL-53.xyz: CrD4C8O5, 72 sites, 72 atoms, P1
```

The first `wrote` line describes the structure that was handed to the
writer, symmetry and all; the file it wrote holds none of it, which
the second conversion shows: read back, the POSCAR is 72 sites in P1.
The second read reports the same cell, formula and density, and a
group of one operation:

```console
$ xtal info MIL-53.xyz
formula        CrD4C8O5  (Z = 4)
space group    P1 (#1, triclinic)
cell           a=16.7720  b=13.1450  c=6.8470
               alpha=90.000  beta=90.000  gamma=90.000
volume         1509.544 A^3
sites / atoms  72 / 72
mass           944.540 amu
density        1.0390 g/cm^3
```

Nothing about the atoms was lost, only the statement of what relates
them, and detection gets it back -- group No. 74 again, reported in
its {term}`standard setting` *Imma* where the CIF had written the
same group as *Imcm*, with the seven {term}`orbits <orbit>` the CIF
had as sites:

```console
$ xtal symmetry MIL-53.xyz
space group    Imma (#74)
Hall           -I 2b 2
point group    mmm
operations     16
orbits         7
standard cell  no
current group  P1 (#1)
hand           chiral, its own enantiomorph
```

:::{warning}
`xtal convert` writes the structure it read.  It does not pass
through the cleaning the *Export…* dialog does ({doc}`export`), so a
workspace CIF that carries markers or a drawn net converted on the
command line carries them into the new file -- and in a format with
no bond loop, a dummy atom becomes an element `X` in somebody else's
program.  Export from the window, or remove the markers first, when
the file is for another program.
:::

## Limitations

- Anisotropic displacement parameters and charges survive only in
  CIF and in a project; occupancy survives in CIF, pymatgen JSON,
  extended XYZ and a project.  The dialog's line is the authority for
  the format you have chosen.
- No format but the project keeps the view, the measurements or the
  planes; no format but CIF and the project keeps the bonds.
- The reader believes the first data block of a CIF and warns about
  the rest; there is no way to choose another block from the window.
- A POSCAR without a species line, a `.gen` with no atoms, and a
  pymatgen JSON that is not a `Structure` are refused with a sentence
  saying why, rather than read as something else.
