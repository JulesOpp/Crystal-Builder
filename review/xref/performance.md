## Numbers he measured that update or contradict the report

- **Finding 4's headline number no longer applies to its own fixture.** The report's 298 MB / 0.571 s figure was measured on Ni2Cl2BTDD, which PR #2 correctness fixes now refuse to load as-is (coincident-atom guard). PR #5 doesn't dispute the report's diagnosis of *why* memory spiked (large `(n,3)` float64 temporaries) — it just re-measures on the input the report's own edge-cases finding says should never have reached UFF in the first place. This is the right call, not a contradiction of substance: the review itself (REVIEW.md §3.4, §6 "Why Ni2Cl2BTDD is expensive") already flagged that structure's degree-28 atoms as a correctness bug masquerading as a perf one.
- **PR #5's own commits update CLAUDE.md's pore-surface numbers** (932d568), which the review had already flagged as stale ("CLAUDE.md records '190 000 triangles and 3 s'... at DEFAULT_SPACING 0.4 it is now 307 680 triangles and 1.07 s, and the note deserves updating either way"). The maintainer did update it, folding in his own smaller memory numbers.
- **The suite's memory-bound framing was re-measured and reversed for one sub-claim**: the report leads with "share one QApplication and build fewer full MainWindows... a real reduction in the suite's resident set." PR #5's `6467c15` measured windows at 25 MB with no leak on this maintainer's machine and reframed the same lever as a *time* fix (85 s of 329 s CPU), not a memory fix. Both diagnoses point at the same code change (fewer/cheaper `MainWindow` construction via a `gui` marker), so this doesn't change what shipped, but it is a genuine correction to the report's causal story.

## Judging the maintainer's approach where he diverged

- **Finding 2 (space group inverses):** shipped exactly as recommended (integer-keyed dict, class/module-level cache). Equal to the report's proposal; nothing to improve on.
- **Finding 4 (UFF memory):** his approach (chunk the pair search *and* the term evaluation, measure on a legitimate large cell) is **better** than the report's own fix suggestion, which only proposed chunking the torsion evaluation and switching shift arrays to `float32`. He found and fixed a bigger contributor (the `neighbor_pairs` full cross-product buffer) that the report's own profiling hadn't isolated, while also declining to chase the `float32` shift-array micro-optimisation (not present in current `terms.py` — shift arrays are still float64) since it wasn't where the memory actually was.
- **Finding 7 (drag/scene rebuild):** his approach matches the report's prescription for the *cheap* half (batched `eigh`, cached substituents) but correctly declined to do the *expensive* half (incremental `p1.expand`/scene diffing) in the same PR, and said so explicitly in `docs/TODO.md` rather than claiming it was done. That is the right call for a "day's work" vs. "hasn't been designed" item — equal in judgment to the report's own S/M/L sizing, which put this in the same "L" bucket as the busy cursor (S) it shipped alongside.
- **"-n auto" (what-would-help #3):** superseding the report's caution once its precondition (the deadlock) was fixed is correct, and he left a paper trail (the `pyproject.toml` comment quoting the original review's own words back) rather than silently reverting — good practice.

## What's still open, ranked by value

1. **Finding 7's harder half: incremental P1 re-expansion and scene diffing for a drag/Supercell.** Explicitly open in `docs/TODO.md` ("A drag and a Supercell still rebuild from scratch"); Supercell 2×2×2 is still ~1.2 s (now under a wait cursor, so at least legible) and drag is 65 ms/step (15 fps, was the review's own headline "sticky drag" complaint). This is the report's own "L" bucket item and the only one of the three "pays back most" recommendations not substantially delivered.
2. **Finding 3's literal fix: stop deriving a bond graph in the enablement path.** Currently works only because `bonding.graph`'s pre-existing memoisation absorbs the redundant call; a future edit that busts that cache more aggressively (or a bigger framework where even one graph rebuild is costly) would resurface the original complaint. Cheap to do now that findings 2 and 6 are shipped — genuinely an S-sized cleanup.
3. **The `float32`-shift-array micro-optimisation from finding 4** was superseded by a better fix, but is genuinely still on the table as free-ish additional headroom if UFF memory becomes a problem again on a bigger structure than MFU-4l 2×2×2.
4. **Nothing in this report's scope remains "not done" outright** — every `[important]`/`[critical]` finding got at least a partial, verified fix; the two PARTIAL items (3, 7) are both explicitly tracked by the maintainer himself in `docs/TODO.md`, which is the right way to leave them.
